## 一、七问根因（代码级）

### 问题 1 · 本纪里也写出了「实为X之子」

**证据链**

1. `facts._villain_chains()`（`facts.py:7291-7322`）产出「托卵承嗣」链：
   `潘杜尔夫·柳特佩特抚养的索丹·柳特佩特、雅各布·柳特佩特、阿盖尔蒙德·柳特佩特，实为索丹·索丹之子。`
2. `facts._protagonist()`（`facts.py:6604-6607`）把它塞进 `p["dramatic_facts"]`。
3. `biography._profile_lines()`（`biography.py:634-637`）渲染成
   `戏剧性事件：…实为索丹·索丹之子；…实为古布莱努·托尔基托留之子。`
4. `biography._shared_facts_block()`（`biography.py:1239`）把【人物档案】整体放进**共享前缀**；
   `build_intro_messages` / `build_lead_messages` / `build_section_messages`
   （`biography.py:1291` / `1327` / `1359`）**每一次请求**都带这段前缀。

实测快照 `shared` 字段（1181 字符）末行即为该句 —— 于是《本纪》开篇与纪事都拿到了「秘密」。

**加重项**：`_article_facts` 给《家室列传》纪事发的是**子女档案**，
子女档案里 `实父卡拉布里亚埃米尔索丹·索丹`（`biography.py:615-616`）是明文；
`facts._secrets_facts()` 的 `kinsmen` 又把配偶的 6 桩隐事整句写进《阴私录》。
同一件事现在有 3 个下发通道、4 处复述。

**修复方向（程序端控制披露面）**

- 披露分级：`公开`（史笔所见：法理谱系、不育之身却屡屡添丁）／`内宅`（家室列传：
  妻室情事脉络，不点名实父）／`揭底`（阴私录：实父、乱伦、把柄）。
- `_protagonist()` 增加 `profile_surface`（去掉 `real_father` 与「托卵承嗣」戏剧链）
  与 `profile_full`；`_shared_facts_block()` 只发 `profile_surface`。
- 子女档案的 `实父X` 只随《家室列传》《阴私录》下发；《本纪》《刺客列传》等只给法理父。
- 提示词侧加一条正向「叙事规则」（见 §二问题1）。

### 问题 2 · 「870年，西法兰克王国公主希尔德加德·加洛林有一桩隐事：乱伦。」

**证据链**

- 熔件原始记录（`melt_870_01_01.json`）形如
  `{"type":"secret_incest","target":[],"owner":27262,"participants":[27262]}`
  —— `target` 恒空，游戏**不在同一条记录里存对方**；真相是「双方各持一条」：
  `77: owner 27262 / 78: owner 27163`。
- `style.SECRET_TOPICS["secret_incest"] = "乱伦"`（`style.py:551`）无 `{target}` 占位；
  `facts.secret_topic()`（`facts.py:2614-2621`）见模板不含 `{target}` 且 `tname` 为空
  → 直接返回 `乱伦`。本地化回退（`facts.py:2622-2626`）同样取不到对象。
- 柳特佩特局的实例：`16777357 {type: secret_incest, owner: 15899, target: [],
  participants:[15899], first_seen: 870.1.1}` —— 持有人是主角配偶希尔德加德·加洛林，
  但句子写不出对方是谁。

**对方是谁（实测可判，但不能靠「同日的恋情」）**

⚠️ 修正：初稿曾据「同日 `secret_lover target=42533 安科马`」推断对方是安科马，**这是错的**——
安科马（42533）无父无母无家族，与希尔德加德**没有任何亲缘**，构不成乱伦。
用户提示「去查秃头查理的相关记忆」，实测（`experiments/diag_charles_mem.py`、
`diag_incest_pair.py`）：

```
秃头查理 12154 的性情记忆:
  871.1.5 had_sex_giving_player_vaginal_cum_inside_consensual → 15899 (Hildegard)
  家族: child = [14819, 14924, 15353, 15602, 15682, 15899, 15987, 16071]   # 15899 是他的女儿

secret 354:  owner=12154 (秃头查理)  first_seen 872.1.1   → 乱伦
secret 16777357: owner=15899 (希尔德加德) first_seen 870.1.1 → 乱伦
```

**真相手是父女：秃头查理 × 希尔德加德（851 年生，其女）**，性情记忆日期 871.1.5。
同一份扫描还查出另外两条：`secret 516 owner=14924`（希尔德加德之妹）与
`secret 515 owner=15602`（其兄弟）——同一门内不止一桩。

**可判规则（程序端能落地）**

`secret_incest` 的对方 = **持有人的血亲** ∩ **与持有人有性/情记忆**（`had_sex*` /
`became_lovers` / `became_soulmates` / `developed_crush`）：
- 血亲只认**血亲**（父/母/子女/同胞），**姻亲（配偶）不算**——
  这正是初稿出错的地方（安科马是情人、主角是配偶，都不是血亲）；
- 取日期最接近 `first_seen` 的那一条；取不到就不点名；
- 判不出时降级为不含对象的形态，交给程序而不是让模型猜。

**修复方向**

- 新增 `Facts._secret_partner(rec)`：实现上面的「血亲 ∩ 性情记忆」判定；
  判不出时**降级**为不点名形态（如「乱伦（对方其人未见于记载）」）。
- 血缘判定复用存档已有的 `family.father/mother/siblings/child`（熔件同源）。
- `SECRET_TOPICS` 补 `secret_incest` / `secret_adultery` 的 `{target}` 模板；
  `_SECRET_PARTY_TARGET_TYPES`（`facts.py:195`）同步纳入 `secret_incest`，
  保证对方不被打成「知情者」（否则又是同义反复）。
- ⚠️ 若沿用「同 holder 平级记录」之类的规则，必须显式排除**配偶**，
  否则会把「夫妻同房」写成乱伦。

### 问题 3 · 天下大势永远有中国官职录

**证据链**

- `Facts._current_ministers()`（`facts.py:2517-2543`）遍历 `self._lt` 里**全部**
  `e_minister_*` 头衔，逐个 `holder_at()`，**无任何政权/上位链过滤**。
- 实测（本次运行的 melt_878 表）：

  ```
  玩家上位链: 2225 c_benevento → 2224 d_benevento（到顶，无宗主）
  9 个 e_minister_*: liege 全为 14036 h_china，liege_holder 13360 李漼（唐皇帝）
  → 天下大势: 朝廷职司：宰相路岩、御史大夫徐商、枢密使杨玄翼、吏部尚书卢词…
  ```

  贝内文托亲王与唐帝国在政治上毫无关系，这 9 个职司却被当成「主角所处朝廷」下发。
- `Facts.minister_ids()`（`facts.py:2545-2557`）同一毛病，`_realm_secret_lines()`
  （`facts.py:6998-7021`）据此把「唐皇帝李漼 / 吏部尚书卢词」的隐事写进《朝局风云录》。

**修复方向**

- `_current_ministers()` / `minister_ids()` 增加**政权门槛**：只收
  `title.de_facto_liege ∈ 主角上位链头衔集` 的职司；
  主角独立无宗主时，本朝职司取其自身头衔（`h_/e_/k_` 级领地）下的 `e_minister_*`，
  无则整块不下发（无料即不下发，已是项目口径）。
- `realm.ministers` 为空时 `_article_facts` 不再拼「朝廷职司：…」行。
- 顺带核对 `holder_changes` 的 `_related_ids` 过滤（本次阿基坦王国那条是**相关**的，
  好友/姻亲曾任，保留合理）。

### 问题 4 · 微小阴茎特质没被收录

**证据链**

1. 主角 `trait_history` 里确有 `dick_small_bad_3`（`RICE` 与 Carnalitas 的 Mod 特质）。
2. 定义在
   `…/mod/Carnalitas/common/traits/carn_traits.txt`：
   `name = { first_valid = { triggered_desc{…immersive} desc = trait_dick_small_3 } }`
   —— 基础名键就是 `trait_dick_small_3`。
3. 用**当前** Mod 环境重跑 `localization.build_trait_names()` → `dick_small_bad_3`
   正确解析为 `trait_dick_small_3`；但 `data/trait_names.json`（已落盘那份）
   **完全没有**这个键（旧表 81 个特质，新表 109 个，差的 27 个全是 Carnalitas 系：
   `dick_*` / `tits_*` / `futa*` / `former_slave` / `lifestyle_prostitute`）。
4. `load_trait_names()`（`localization.py:1357-1372`）只在
   `schema != 3 或缺 traits/categories/level_names` 时重建；**不校验内容指纹**
   （对比：`load_localization_table` 有 Mod 指纹比对，会自动重建）。
   → 陈旧表被一直用下去。
5. `_trait_name()`（`facts.py:354-375`）候选链
   `[档位名, trait_names.traits[key], trait_<key>, key, TRAIT_ZH]` 全部落空 → `''`；
   `trait_groups()`（`facts.py:4363-4365`）与 `_trait_pairs_at()`（`facts.py:4343-4346`）
   都以 `if z` 过滤 → **静默丢弃**，日志里也看不出来。
   旁证：`beauty_bad_3`／`intellect_bad_3` 之所以正常显示「面目狰狞」「痴呆」，
   靠的是 `facts.TRAIT_ZH` 硬编码兜底，不是解析成功。

**修复方向**

- 给 `load_trait_names` / `load_trait_tracks` 加**内容指纹**（Mod 目录列表 + 特质文件
  mtime/size 哈希），指纹不符即自动重建（与本地化表同法，符合「启用 Mod 的本地化生效」口径）。
- `TRAIT_ZH` 不再承担兜底职责之外的角色：解析失败即写 `logs/loc_miss.log`，
  并把「档案里出现但没有中文名的特质」列成一次性报告，避免下次再静默丢。
- 补一条 `verify_fast.py` 断言：主角 `traits` 里的每个键都要能在 `traits_sentence()` 里出现。
- **需拍板**：`dick_small_bad_3` 属「禀赋」（`category` 为空 → 归「禀赋」），
  修好后档案会写出「禀赋…、极小阴茎、…」。要不要写进正式传记，请给口径
  （三选一：①照写；②归入不入正文的「体况」隐去；③只保留不育这类语义正当的禀赋）。

### 问题 5 · 【人物档案】每板块都传 → 各篇车轱辘话

**证据链**（快照实测）

- 共享前缀 1181 字符含：【传主】【家族】【现状】+ **完整【人物档案】** + 【概览】+
  【主角大事摘要】（逐年一行）。
- 共享前缀被 `build_lead_messages` / `build_section_messages` **每次请求**原样带上
  （为前缀缓存命中）。
- 同一信息的多通道重复：
  - 主角档案 → 共享前缀（14 次）× 《本纪》板块 × 《朝局》板块「其廷中职司，井然有序…」；
  - 【主角大事摘要】逐年行 ↔ 各篇 `大事年表` / `传主行迹` / `朝局动态`（同一批时间线文本）；
  - 配偶与子女档案 → 《家室列传》开篇（配偶）+ 纪事（子女）+ 《阴私录》kinsmen。
- 结果：每篇的**独有素材**被共享素材淹没，模型只能把同一件事换个说法再讲一遍
  （用户观察到的「车轱辘话」）。

**修复方向（瘦身 + 分篇切料 + 正向写作规则）**

1. 共享前缀只留「稳定最小身份票」≈200 字：
   `【传主】姓名｜【家族】｜【现状】｜【概览】一行`；
   把【人物档案】与【主角大事摘要】移出共享前缀。
2. 【人物档案】改为**按篇给**：本纪与总纲给主角档案；其它各篇给**本篇传主**的档案，
   不再给主角档案（主角信息由开篇摘要与「相关事实」承担）。
3. 时间线分片：本纪纪事给完整年表；其它篇只给**本篇切片**（`F.slice_timeline` 已按
   `MODULE_SLICE` 分模块，把共享的逐年摘要去掉即可）。
4. 篇目「唯一职责」进 `articles`：每篇一条 `focus`（本纪=公开生平、家室=门庭内情、
   阴私=秘密揭底、刺客=死者小传…），写进总纲预告与各篇要求，
   使「哪篇讲哪一层」成为程序给定的事实。
5. 加断言：共享前缀 ≤ 400 字符；各篇 `facts` 块与共享前缀零重叠（逐块 diff）。

### 问题 6 · 家族恩怨录把「围攻被俘」当成结仇之由

**证据链**

1. 《家族恩怨录》开篇写成「结仇是因为主角把斯巴达诺斯家的人锁进牢里」，
   纪事的因果链收束为
   `868年宣战 → 868年12月7日囚禁格里戈里奥斯三世 → 875年1月2日再宣战 → 875年6月29日囚其三人 → 875年7月2日正式结仇`。
2. 快照 `facts.house_feuds`（唯一数据源）给的就是这七条流水，
   **两条 `war_won` 与那条 `lost_title_memory` 都不在其中**：

   ```
   868.7.30 向那波利伯爵格里戈里奥斯三世·斯巴达诺斯宣战
   868.12.7 囚禁了那波利伯爵格里戈里奥斯三世·斯巴达诺斯
   875.1.2  向那波利伯爵格里戈里奥斯三世·斯巴达诺斯宣战
   875.6.29 囚禁了凯撒里奥斯·斯巴达诺斯 / 妮卡蕾忒·斯巴达诺斯 / 卡利斯托斯·斯巴达诺斯
   875.7.2  成为格里戈里奥斯·斯巴达诺斯的仇敌
   ```

   来源是 `house_relations.database.<id>.history` 的 `change_reason` 原文
   （`facts.house_feuds()` / `_rerender_feud_event()`，`facts.py:3231-3310`、`2128-2141`），
   该 history 本身只记「关系值变化的那一件事」，不记战争胜负与夺地。
3. 缓存记忆里真正的因果链完整可读（`player_38653.json`）：

   ```
   主角:  868.7.30 offensive_war  {other_party:12417}   war_cb_fallback
          868.12.10 war_won        {winner:38653, loser:12417}
          875.1.2  offensive_war  {other_party:12417}   war_cb_conquest
          875.7.2  war_won        {winner:38653, loser:12417}
          875.7.2  became_rivals  {rival:12417}
   对方:  875.7.2  war_lost       {winner:38653, loser:12417}
          875.7.3  lost_title_memory {new_holder:38653, reason:"conquest",
                                       landed_title:2240 (那波利伯爵领)}
   ```
   即：**先两次宣战并取胜，再夺其头衔（2240 那波利伯爵领），对方沦为无地冒险者，随后结仇**。
   868 年那次的次序尤其说明问题：12 月 7 日围城中俘人（记一条囚禁），12 月 10 日战败——
   「囚禁」是战役过程里的一步，而不是两家反目的起点。
   游戏的 `house_relations.history` 只把「关系值变动的那一下」（囚禁）记了进去，
   战役的起因与结局（宣战、胜负、夺地）全在缓存记忆里，没进这段恩怨史。
4. 现状下模型只拿到中间结果，于是把「囚禁」读成动作、把「结仇」读成反应，
   自行补上「绑人泄愤」这类动机。程序侧本可给出整条链，却没有。

**修复方向**

- `house_feuds()` 的 `events` 改为**因果链叙述**：在关系流水之间插入
  「开战 → 战败 → 失守某头衔 → 沦为无地冒险者」节点，
  由 `offensive_war/defensive_war`（`other_party`）+ `war_won/war_lost`

  直接渲染；`war_cb` 是 `conquest` 时写「征服战」，`fallback` 时写「开战」。
- 补「沦为无地冒险者」事实：检查该家族成员在 `lost_title_memory` 之后
  是否已无领地头衔，是则给一句「此后沦为无地冒险者」——
  这正是「为什么记恨」的答案（本怨录现在完全没有）。

## 二、写作层方案：从「复述」改成「决定性瞬间」（对应问题 5、1）

> 依据见 §四 Web 调研。核心结论：**一篇只承担一个侧面，侧面由「主题词 + 一个决定性场景」
> 定义，而不是由生平时间轴定义**；同一人的多篇用《史记》互见法分片。

1. `style.py` 增 `RULES["narrative"]`（正向表述，纳入 `_RULE_ORDER`）：
   「每一篇先立一个主题词与一个决定性场景（日期 + 地点 + 一个动作），
   全篇段落都服务这个主题词；每段推进新信息、新关系或新后果；
   让主角经他人的眼睛被看见；结尾回到开篇那个场景，让读者看见这一篇里的变化。」
2. `style.py` 增 `RULES["secret"]` 补充段（只随携带秘密的板块下发）：
   「秘密首次写出时，给出**具体日期、做过什么、谁在何时知情**；
   本篇之外，同一事实只以公开面貌出现一次并一句指代。」
3. 每篇一个 `focus` 句子（主题词 + 首发篇目），进总纲预告 + 各篇要求（见 §一问题5.4）。
4. 事实层「一料一处」：为每份事实指定**唯一首发篇目**（本纪优先），
   其余篇改给该篇切片或一句指代。
5. 叙事者「已知范围」按篇限定（本纪=公开、家室=内宅、阴私=揭底），
   使「延迟揭示」成为分篇的天然产物，而不是提示词里的禁令（见 §四·四）。

### 二·一 拟进 `style.RULES` 的「分篇规则」候选（13 条，正向表述）

> 全部来自 §四调研；建议先落**加粗的三条**（见效快、改面小），其余按篇逐步加。

1. 每篇动笔前先定一个**主题词**，全篇段落都为之服务。
2. 每篇开篇写一个**只属于本篇的决定性场景**，把人物放进正在发生的动作里。
3. 每篇只提出**一个中心问题**，结尾给出回答或明确留白。
4. 每篇选一个**不同的入场人物或视角**，让主角经由他人的眼睛被看见。
5. **每份事实分配一个首发篇目**，该篇详写，其余篇以称呼或一句指代带过。
6. 每段提供**新信息、新关系或新后果**。
7. 每处细节落到**具体感官、物件或动作**上，让评价由细节自然生出。
8. 每篇为前文已知的秘密安排一条**可回溯的伏笔**，把揭示放在本篇转折处。
9. 每篇用一组**对比或镜像人物**映射主角的某一个侧面。
10. 每篇**结尾回到开篇的场景或句式**，让读者看见这一篇里的变化。
11. 每篇按「**场景—背景—场景**」配比叙事与说明，保持场景占主导。
12. 同一人物的多篇**共用同一套称谓与时间锚点**，使各篇互相咬合而不复述。
13. 完稿自检：本篇主题词之外的事实压缩为一句指代，篇幅让给本篇独有的场景。

### 二·二 与「已有分片机制」的关系

`_split_span` / `MODULE_SLICE` / `F.slice_timeline`（v27 的「同请求内不重复同块」）
已经解决了**同一篇内**开篇与纪事的重复；本方案要解决的是**跨篇**重复，

## 四、Web 调研：决定性瞬间式传记怎么写

（调研结论，含来源；完整报告另存 `docs/调研_多侧面传记写法.md`。）

### 五·一 同一个人的多个侧面怎么处理

**核心结论：一篇只承担一个侧面，侧面由「主题词 + 一个决定性场景」定义，而非由生平时间轴定义。**

1. **先定一个主题词，再选材。** 丹麦《政治报》Line Vaaben 把整篇故事压缩成**一个词**
   （SURVIVAL／LONELINESS），便签分两色——红色是场景与细节、黑色是背景与事实，
   服务不了那个词的材料不进场。
   [来源](https://niemanstoryboard.org/2022/02/02/sticking-a-story-together-and-nailing-the-structure/)
2. **多个侧面靠「编织」（braid）。** Rothman 写 Hinton 的《纽约客》长篇：
   从一开始就把科学与人生编在一起，「让所有元素一起向前推进，
   而不是把它们塞进各自独立的区块」。
   [来源](https://niemanstoryboard.org/2024/06/06/profiles-artificial-intelligence-interviewing-geoffrey-hinton-story-structure/)
3. **用一个物件承担主题**：Hinton 拿出一只刚羽化的蜻蜓讲幼虫化成「汤」，
   隐喻神经网络训练，意义由人物当场说出。（同上链接）
4. **以决定性场景作骨架**：Rothman 把四天岛屿拜访当叙事脊柱——场景是筛选器，
   能放进这条时间线的事实才进正文。（同上链接）
5. **开篇从最精彩处切入**：《人物》主笔谢梦遥——「直接从最精彩的部分开始」，
   时间交代挪到第二句之后，常用局部特写开篇（一双手、一张脸）。
   [来源](https://www.sohu.com/a/287941626_375507)
6. **他人视角侧写主角**：写陈冠希从司机龙哥写起；写马东先让批评者梁欢出场。
   [来源](https://www.sohu.com/a/287941626_375507)
7. **中国古典「互见法」就是「一人多篇」的原型**：《史记》五体分工，
   同一人物材料分散各篇、只取所需，「克服了编年体不能即一人而各见其本末的缺陷」。
   [来源](https://baike.baidu.com/item/%E6%98%A5%E7%A7%8B%E7%AD%86%E6%B3%95/153951)

### 五·二 「决定性瞬间」可操作技巧（12 条）

1. 开篇写**具体时刻的具体动作**，第一段出画面、第二段出人名或引语；
2. 全篇只解决**一个悬念**，其余信息挂在这个悬念上；
3. 每段都**推进**：新信息、新关系或新后果；
4. 细节取自**感官与动作**（矿工特稿：买鞭炮、退遗像、退寿衣）；
5. 用**他人视角侧写**主角，对手／下属／配偶各一句；
6. 用**对比与反差**（马东 vs 梁欢）——反差本身就是解释；
7. **结尾回到开头场景**（写张伟以「中国有超过 40 万个叫张伟的人」开篇，结尾复现并翻案）；
8. **中段制造错觉**再揭示；
9. 让**主角稍后出场**或由配角引入，前提是两条线后文多次交缠；
10. 结尾**开放式或戛然而止**；
11. 把生平**分摊到若干场景**便签再定结构（直线／多线编织／场景—背景—场景）；
12. **转折点决定篇幅**：先做时间轴，挑 2–4 个转折点详写，其余几句带过。
    [来源1](https://www.sohu.com/a/287941626_375507)
    [来源2](https://www.storiestotellbooks.com/blog/writing-a-life-story-focus-on-the-turning-points.html)

### 五·三 「信息分片」的对应做法

1. **互见法即天然分片**：本传详述主线，他传只取与本篇主题相关的一面，材料互见而不重出；
2. **一篇一词**：同一事实只在最贴切那篇详写，其余篇以一句指代；
3. **一次性详述、永久指代**：为每份事实指定唯一「首发篇目」；
4. **编织而不分区块**：同一素材在不同段落承担不同功能；
5. **同题不同篇**：谢梦遥一个月内写同一人物两篇稿，靠换入场人物、换切入场景、
   换开篇视角做到素材不重样；
6. **素材先分组再定次序**：先建逻辑大框架，再把素材填进去。
   [来源](https://www.thepaper.cn/newsDetail_forward_2637343)

### 五·四 「延迟揭示」的 8 条写法

1. **先立悬念，后给身份**：McPhee《Travels in Georgia》跟访过半才交代职业；
2. **用可回溯的物证埋线**：线索当时显得合理，事后读者能对上；
3. **给每篇指定已知范围**：叙事者知道全部，文本只出现他当时能知道的信息；
4. **多重见证先行交织**：借旁人回忆预告「出了事」，隐藏是谁、为什么；
5. **假象与延后修正**：虎口事故开篇写平静病房，后半程才揭晓；
6. **线索引而不发**：同一物件第二次出现时改变含义；
7. **分篇承担秘密**：真正的隐事放进专篇（阴私录），其他篇只留一处无从解释的异样举动；
8. **延迟意义而非事实**：事实前文照常陈述，因果与代价留到后文。
   [来源1](https://niemanreports.org/deliberating-withholding-information-to-create-suspense/)
   [来源2](https://www.writersdigest.com/how-to-plant-clues-without-giving-away-the-ending)

> 对本项目最直接可用的三条：**每篇一主题词**、**每份事实指定唯一首发篇目**、
> **限定每篇叙事者的已知范围**——第三条正好把「延迟揭示」变成分篇的天然产物
> （对应问题 1 的披露分级与问题 5 的分片）。
