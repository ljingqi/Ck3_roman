# 跨战役读取审计（2026-09-10）

> 触发：陆氏问题 3（`names.json` 把 16293 写成另一战役的「藤原利仁」）暴露了一类缺陷——
> **角色 id 只在同一存档/战役内有意义**，任何按 id 索引的全局数据都可能跨战役错配。
> 本文逐条排查数据来源、读文件点与缓存/熔件配对逻辑，列出已修项与残留风险。
> 状态：**已修（提交 `c16d3f1`），确定性回归全 PASS。**

## 0. 结论

| # | 位置 | 风险 | 处置 |
| --- | --- | --- | --- |
| 1 | `cache_lib.display_name` 用全局 `data/names.json` | **已证实错名**（16293 郑良士→藤原利仁；全档 27662/50261 名不符） | 熔件角色优先 + 表内 `playthrough_id` 不符即弃用（`44c22ce`） |
| 2 | `build_names.py` 默认取**所有战役文件夹里日期最新**的 melt | 表内容跨战役 | 写战役号；新增「战役内副本」`output/<家族>/data/names.json`；传记优先读副本（`c16d3f1`） |
| 3 | `cache_lib.extract_snapshot` 只校验 `player_id` | 同 id 的另一战役熔件可并入本缓存（867 自定义角色 id 恒定，极易撞） | 新增 **playthrough_id 校验**，不符即拒收并打印跳过原因（`c16d3f1`） |

| 6 | `pipeline._cross_check_deaths` | 可把本战役的死亡记录写进**另一战役的缓存** | 两战役号都存在且不同即跳过该缓存（`c16d3f1`） |

## 1. 逐条证据

### 1.1 `data/names.json`（已修，`44c22ce` + `c16d3f1`）

- 结构：`{schema, source, total, names:{<角色id>: {name_zh, house_name, dynasty_name}}}`，
  `source` 只是**生成时那一份 melt 的日期**（实测 `1074.1.14`，与陆氏战役无关）。
- 实测陆氏 `melt_878`：27662 / 50261 个角色的本名与该表同名 id 记录不一致。
- 修法：`display_name` 取值链改为 缓存 → **熔件角色**` → names.json；
  `_load_names(names_path, melt)` 在表有 `playthrough_id` 且与熔件不符时返回空表；
  `build_names.py` 写战役号 + 在 melt 所属战役文件夹写一份副本；
  `biography._names_path` 优先战役内副本，全局表只作兜底。

### 1.2 `extract_snapshot`（已修）

```python
# cache_lib.py  (v28 新增)
_cpt = cache.get("playthrough_id"); _mpt = melt.get("playthrough_id")
if _cpt and _mpt and str(_cpt) != str(_mpt):
    print(f"  [跳过] 档期 {date_label} 战役 {_mpt} 与缓存战役 {_cpt} 不一致")
    return False
```

- 为什么必要：v18 之后**调用方**（`_process_save` / `_catchup` / `_cross_check_deaths`）都按
  `playthrough_id` 选缓存，但 `step_rebuild_cache` 的**旧根目录分支**只按 `player_id` 归并
  （`pipeline.py:1541` `built[player_id]`），所有根目录熔件会并进同一份缓存。
  写入点是唯一的，防在写入侧最可靠。
- 兼容：两边都有战役号才校验 —— 空缓存（新建）、无 `playthrough_id` 的老熔件行为不变。

### 1.3 熔件取用（已修）

- `melt_path_for_cache`：战役文件夹内找不到时回退 `data_dir/melt_<日期>.json`（旧布局）。
  现在回退前校验战役，不符即 `return ""`（调用方一律 `os.path.isfile` 判定，四处调用点已核）。
- `load_latest_melt`：把「载入 + 校验」收进内部 `_load()`，不一致就跳过并继续回退；
  传记事实源头因此绝不会拿到他战役的熔件。

### 1.4 死亡回填（已修）

- `_cross_check_deaths` 原本 `hits.sort(key=... != melt_pt)` 只是**把同战役排前面**，
  若只有他战役缓存且名字恰好一致，仍会把死亡记录写进去。
  现在两战役号都存在且不同 → `continue`（不同战役的缓存绝不接收本战役的死亡记录）。

## 3. 残留风险与建议

1. **`build_names.py` 不传参时的默认选择**仍是「全局最新 melt」。表本身已无害
   （读时校验战役 + 熔件优先），但正确用法是显式传本战役熔件；已写入 docstring 与 README。
2. **旧缓存（无 `playthrough_id`）**：校验条件要求两边都有战役号，这类缓存仍走名字相等兜底。
   新战役一律写入战役号，属历史数据的一次性过渡。
3. **同宗族文件夹复用**：`determine_folder` 会为新战役加序号，但若手工把两战役熔件放进同一
   `output/<家族>/data/`，`extract_snapshot` 现在会拒收后者（日志可见），不会静默缝合。
4. `_iter_melts` 仍会遍历所有战役文件夹（`rebuild-cache`/`index-melts` 需要），
   但它们只做「按文件夹归属」的重建与边车生成，不产生跨战役合并。
