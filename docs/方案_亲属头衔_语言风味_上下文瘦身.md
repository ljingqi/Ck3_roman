## 零、结论摘要

| 任务 | 结论 | 核心证据 | 风险 |
|---|---|---|---|
| 1 亲属补头衔 | **可行且成本极低**。渲染层已有全部能力（`official_title` / `_last_high_title_before` / `_ruler_word_at` / `prince_title`），只差一个统一的「亲属标签」出口。原型已跑通：`妻父 毗伽庞特勤 → 曾任高昌国王毗伽庞特勤`；`塔坦尼·布兰 → 可萨布兰部可敦塔坦尼·布兰`。全区 215 人可命中公主/王子/郡主/皇女称号。 | §二·2、§二·4 | 头衔选中口径（现任 vs 历任 vs 称号）、同名额冲突 |
| 2 语言风味 | **数据齐备、零新增采集成本，当前被完全丢弃**。`Facts.languages()` 已把 124 种语言 100% 中文化，35/39 个进提示词的角色带语言字段，但 `biography._profile_lines` **一行都没渲染**。可做三层风味：档案行 → 人物关系（同语/异语）→ 情节（通译、笔谈、学语）。 | §三·2、§三·3 | 语言字段在死者身上被清空（需 graceful 省略） |
| 3 上下文瘦身 | **「词元太多」的病灶不在总量，而在三处结构性重复 + 一个度量缺失**。实测：同一请求内 `【人物档案】` 与「人物档案」**逐字节重复两次**；6 篇里 5 篇 lead 与 mid 的**事实块完全相同**（终传 12,721 字符纯重复）；中段回贴开篇全文。D:\Journal 的对照优势正是「每个板块一个专属数据渲染器」。模块表 `MODULE_TABLE` **早已算好并挂在每条时间线事件上，却从未用于切片**。 | §四·2、§四·3 | 切片造成的跨模块断链（有对策） |

**一句话**：任务 1、2 是「把已有数据接出来」，**合计新增约 200~500 字符/次生成**；任务 3 是「删重复、按主题切片、把度量补上」，**可减 22%~29% 字符，并把每请求中位从 4,200 压到约 2,700 字符（接近 D:\Journal 的 2,000）**。

### 1.3 三处结构性重复（取证为「逐字节相同」）

| # | 重复 | 取证 | @900 代价 | @901 代价 |
|---|---|---|---|---|
| R1 | `【人物档案】` 出现在**同一条消息里两次** —— `_shared_facts_block`（biography.py:1003）已给了主角档案；`_article_facts` 的 `blocks["人物档案"]`（biography.py:741/793/816/870/897/904/927/937/950）又给一遍，**内容逐字节相同** | `pa == profile → True`（本纪/家室/朝局/刺客，共 4 篇） | 4 篇 ×2 板块 ×527 = **4,216 字符** | 10 请求 ×590 = **5,900 字符** |
| R2 | 同一篇的 **lead 与 mid 事实块完全相同** | `b1 == b2 → True`（本纪/好友/仇人/家室/朝局 5 篇；刺客列传因 v11 已切片而不同） | **11,260 字符** | **12,721 字符** |

> D:\Journal 的对照实现：`SECTION_FACTS`（magazine.py:176）+ `render_facts`（magazine.py:1566）
> 为**每个板块指定一个专属渲染器**（`_facts_front` / `_facts_soldier` / `_facts_homefront` …），
> 板块之间数据**不重叠**；且 `_lead_digest`（magazine.py:1746）把开篇压缩成「前缀 260 + 结尾 180」，
> 只有罪案类才回贴全文。Roman 目前的 lead/mid 几乎是同一份数据发两遍。

### 1.4 度量缺失（最重要的发现）

`llm.call_deepseek`（llm.py:197-255）**只读 `choices[0]`，完全不看 `usage`**。
因此项目从来没有拿到过 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，
「词元太多」这个判断一直**没有可归因的证据**。

而 DeepSeek 的定价结构决定了「总量」不是正确的度量：

| deepseek-flash 百万 token | 缓存命中 | 缓存未命中 | 倍率 |
|---|---|---|---|
| 空闲时段 | 0.02 元 | 1 元 | **50×** |
| 高峰时段 | 0.04 元 | 2 元 | **50×** |

> 依据：[模型 & 价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)；
> 缓存规则：[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)
> ——「每次请求会在 **user 输入结束位置** 与 **模型输出结束位置** 各产生一个缓存前缀单元；
> 命中要求**完全匹配**某个已持久化的前缀单元」，另有「多请求公共前缀检测」与
> 「长输入按固定 token 间隔切分」两条机制。

**对 Roman 的直接含义**：
- 每个请求开头的 `system + 共享前缀` 是稳定的公共前缀 → 可被「公共前缀检测」持久化并命中（第 2 阶段起、跨请求）；
- 而 **R1 / R2 的重复落在消息中部（后面还有指令文本），永远无法命中** → 是**实打实的未命中 token**，才是最该砍的部分。
- 所以优化目标应从「字符总量」改为「**未命中 token / 请求**」，并把 `usage` 打出来形成闭环。

## 二、任务 1：亲属列表补头衔（含公主王子）

### 2.1 现状取证：同一个人在两处两种称谓

`experiments/profile_dump.txt`（田所2 @900）实测：

```
--- 仇人 尤拉特 (16796755) 的档案
    妻室亚萨尔、塔坦尼·布兰，子巴哈图尔·布兰，女亚萨尔·布兰。   ← 亲属行：纯姓名
--- 塔坦尼·布兰 (16810341) 自己的档案（同一份提示词里）
    可萨布兰部可敦塔坦尼·布兰，可萨人，信艾什尔里派，生于873年5月2日。  ← 名号行：带头衔
    历任881年10月14日任可萨布兰部至高女王；893年4月28日任洛佐瓦女首领（让出可萨布兰部）。
```

`experiments/verify_ctx_plan_out_901.txt` 同理：

```
妻室周子、毗伽伊尔盖、京代什，子田所秀茂…          ← 亲属行「周子」无绰号
温柔者周子，大和人，信艾什尔里派，生于839年。        ← 档案首行「温柔者周子」
　正妻：周子                                        ← 世系表又是第三种写法
```

**三个问题**：
1. **头衔丢失**：亲属行/世系表一律走 `f.name_or(cid)`（facts.py:774），只给姓名。
   `妻父毗伽庞特勤`（曾任高昌国王）、`塔坦尼·布兰`（可萨布兰部可敦 / 至高女王）全被抹平。
2. **统一显示名丢失**：亲属行不走 `name_with_regnal`，所以绰号（v21）、世系编号（v17）、
   天皇座称号（v20）在亲属行里全丢 —— 同一个人三处三种写法。
3. **同名歧义**：尤拉特家有 `妻室亚萨尔` 与 `女亚萨尔·布兰`，纯姓名无法分辨，加了头衔立刻可辨。

### 2.2 数据可用性：不需要任何新的存档解析

| 需要的头衔 | 已有入口 | 说明 |
|---|---|---|
| 现任头衔/官职 | `Facts.official_title(cid, date)`（facts.py:1745） | 已覆盖活人 + **死者**（`dead_data.flavor` 优先）+ 宗教领袖 + 家族/庄园头衔 |
| 无头衔者的王子/公主称号 | `Facts.prince_title(cid, date)`（facts.py:2016） | 按父母最高层级 × 政体 × 独立 × 性别，返回「楚国郡主」「代国王子」「哈希姆哈里发国皇子」「塔希尔苏丹国公主」 |
| 天皇座子女 | `name_with_regnal` 内已并入（利永亲王） | 不需要额外处理 |
| 已失位/身故者的头衔 | `_last_high_title_before(cid, date)`（facts.py:823）+ `_ruler_word_at`（facts.py:1322）+ `title_base_name` | 毗伽庞特勤 843 年高昌国王，864 年卒，`_primary_title_at` 已返回 None，必须走这条兜底 |
| 头衔中文层级词 | `_name_at_date` / `_ruler_word_at` / `localization.py` | 政体/文化感知（王/可汗/亦都护/大酋长/苏丹） |

**量化（`experiments/proto_kin_title_out.txt`，田所2 @900）**：
- 缓存 15,732 人中，`prince_title` 非空 **215 人**（代国王子、楚国郡主、燕国郡主、
  葛逻禄王国王子、塔希尔苏丹国公主、哈希姆哈里发国皇女、瑞典王国王子…）；
- 3,889 人有历任头衔；
- 主角相关集 17 人中 2 人有头衔、0 人命中称号（田所2 主角是县级游牧酋长，子女无封号）——
  说明「公主王子」路径要靠更大规模剧本才显现，但代码路径已可用。

### 2.3 方案：新增统一出口 `Facts.kin_label(cid, date=None)`

一个方法解决全部三处（亲属行、世系表、好友仇人档案的家属行、妻族传），优先级：

```
① 宗教领袖（religious_head_word）        → 「教宗X」「哈里发X」
② official_title(cid, date) 非空         → 「可萨布兰部可敦塔坦尼·布兰」
③ _last_high_title_before + _ruler_word_at → 「曾任高昌国王毗伽庞特勤」
④ prince_title(cid, date)                → 「楚国郡主苗映娘」
⑤ 其余                                    → name_with_regnal(cid, date)（保留绰号/编号）
```

**原型已跑通**（`experiments/proto_kin_title.py`，只读，未改生产代码）：

```
[正妻]   周子          → 温柔者周子                       ← 修统一显示名
[妻父]   毗伽庞特勤     → 曾任高昌国王毗伽庞特勤              ← 补头衔
[同族女] 塔坦尼·布兰    → 曾任可萨布兰部至高女王塔坦尼·布兰      ← 补头衔
[尼西·布兰] 尼西·布兰     → 曾任可萨布兰部至高王尼西·布兰
[仇人]   尤拉特         → 尤拉特                          ← 无头衔保持简洁
尤拉特 的家属行：侧室「塔坦尼·布兰、亚萨尔」→「曾任可萨布兰部至高女王塔坦尼·布兰、亚萨尔」
毗伽伊尔盖 的家属行：父「毗伽庞特勤」→「曾任高昌国王毗伽庞特勤」
```

### 2.4 本次原型暴露的两个既有缺陷（顺手修）

1. **`prince_title` 会把朝廷职司头衔当「国」前缀**：
   实测 `刘鸣鹤 → 兵部国皇女`、`刘进思 → 兵部国皇子` —— 父/母的首要头衔是
   `e_minister_of_war`（兵部，tid 15783），被 `title_base_name` 渲染成「兵部」再加「国」。
   对策：`prince_title` 的父头衔候选里排除 `e_minister_*` / `x_*` 等非领地头衔，
   无合格候选时返回空。
2. **`曾任` 语义要写清**：亲属行里出现「曾任高昌国王毗伽庞特勤」是准确的（864 年已卒），
   但若同一行出现多人，「曾任」只修饰紧跟其后的头衔 —— 建议在行首统一给一次
   （`父：曾任高昌国王毗伽庞特勤；母：佩克申`），或改用中性写法
   `故高昌国王毗伽庞特勤`。**待裁决，见 §六·1**。

### 2.5 提示词侧（正向表述）

`_profile_lines` 已用「父X，母Y，兄弟姊妹Z」的正向锚点，新方案只需把「X」换成标签串，
提示词本身**一个字都不用加**。若要把「同一人全篇同一称谓」写死，建议在 system 规则里加一句：

> 「亲属与相关人物一律用资料给出的头衔加姓名书写（高昌国王毗伽庞特勤、可萨布兰部可敦塔坦尼·布兰）；
> 同一人在全篇各处用同一称谓。」

### 2.6 成本

- 数据侧：`kin_label` 只对**已在 `_profile_needed_ids` 里的数百人**调用（既有的按需计算，v13），
  且 `_primary_title_at` / `_hold_intervals` / `name_with_regnal` 都有缓存 → 增量可忽略。
- 提示词侧：每命中一人 **+8~14 字符**。田所2 只有 2~3 人命中 → **+30 字符/次生成**；
  一次性命中的大剧本按 10 人估 → +120 字符。相对 §四 的减量完全可忽略。

### 2.7 验证口径

- `experiments/research_kin_titles.py`：打印相关集每人 `official_title` / `prince_title` / `held_titles`；
- 新增 `experiments/verify_kin_label.py`：对田所 / 田所2 全量角色跑 `kin_label`，
  断言「同一 cid 在 5 处渲染（本纪档案 / 家室档案 / 世系表 / 好友仇人档案家属行 / 妻族传）**字符串一致**」；
- 回归点：`塔坦尼·布兰`、`毗伽庞特勤`、`毗伽仆骨`（高昌亦都护）、`亚萨尔·布兰`（至高女王）四条。

## 三、任务 2：语言作为文本风味

### 3.1 现状取证：数据齐全，但从未进入提示词

- `Facts.languages(cid)`（facts.py:2759）已把 `language_norse` → `诺斯语`；
- `_protagonist` 写入 `p["languages"]`（facts.py:4122），`_character_profiles` 写入 `prof["languages"]`（facts.py:4395）；
- **`biography._profile_lines` 全文没有 `languages` 这个词**（grep 实测仅 2 处命中，均为 `prince`）。
  → 语言字段**只存在于内存，从未进入任何提示词**。**这是纯渲染层遗漏，不是数据缺口。**

### 3.2 数据质量实测（`experiments/research_lang.py`，田所2 @900）

```
熔件全体语言 id 共 124 种，无法中文化的 0 种        ← 本地化 100% 覆盖
每人语言数分布：0 语 26,665 / 1 语 32,865 / 2 语 3,210 / 3 语 265 / 4 语 22 / 5 语 7
进提示词的 39 个角色中，35 个带语言字段
```

`culture_manager.cultures[*].language` 给出**文化→语言**映射，可据此区分
**母语（本族语）与习得语言**；存档中**没有** `court_language` 字段（实测全为 None），
所以「宫廷用语」这条路走不通，但「母语 vs 通晓他族语」这条路成立。

### 3.3 三层风味设计（由浅入深，可分别开关）

**L1 档案行（事实锚点，必做）**

`_profile_lines` 的名号句后补一行（无语言记录者整句省略）：

```
通日琉语、乌古尔语。
母语日琉语，兼通乌古尔语。
```

39 个角色约 35 人会各多一行，每行 8~16 字符。**代价：家室档案 +150 字符、主角档案 +12 字符。**

**L2 亲属/关系行（关系锚点）**

亲属行按与主角的语言关系落笔（数据可判定，无需模型推理）：

```
妻室温柔者周子（通日琉语）、毗伽伊尔盖（通共同突厥语）、京代什（通乌古尔语）
```

更有价值的是**语言不交集**——这是历史感极强的素材，且是纯数据判定：

| 人物 | 语言 | 与主角（日琉语+乌古尔语） |
|---|---|---|
| 正妻 周子 | 日琉语 | 相通 |

### 4.5 注意力兼顾（不是只删，还要「看得见」）

依据：[Lost in the Middle（Liu et al., TACL 2024）](https://aclanthology.org/2024.findings-acl.890/)
—— 上下文利用呈 U 型，**开头与结尾利用最好，中部性能下降 20 个百分点以上**；
[Chroma Context Rot（2025）](https://www.trychroma.com/research/context-rot)
—— 输入 token 增长本身即导致性能下降，无关内容（distractor）会叠加放大。
再叠加「重复段落」这一最典型的 distractor。

据此定四条排版纪律：

1. **首**：`system 规则（最稳定，缓存友好）` → `共享前缀【传主】【家族】【人物档案】【现状】【概览】`。
2. **中**：本板块专属的**切过片的**事实块（每段只出现一次，无重复）。
3. **尾**：`【本板块大事】`（3–6 条关键日期一行摘要，程序从切片事实里抽取，
   例：`893年4月28日 塔坦尼·布兰忧惧而亡`）→ `板块要求` → `篇幅要求` → `输出格式`。
   把最需要命中注意力的锚点放在**结尾**（U 型右端）。
4. **一条素材只出现一次**：同一事实只在「切片的板块」或「共享前缀」之一出现。

另有一条可选的**缓存友好性**改进：把 `system` 与 `共享前缀` 之间的边界固定，
让 `system + 共享前缀` 成为所有请求（含总纲、lead、mid）**逐字节一致的最长公共前缀**
（现在 `build_intro_messages` 在 `shared` 之后插了「篇目预告」，`build_lead_messages`
插了「【总纲】」，公共前缀长度已不错；建议核对后固定顺序）。

依据 DeepSeek 的缓存规则（[上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)），
命中要求**完全匹配一个已持久化的前缀单元**，而前缀单元产生于「user 输入结束位置」「模型输出结束位置」
「公共前缀检测」「固定 token 间隔」四处。当前 `generate_biography`（biography.py:1583/1604）
用 `max_workers=len(...)` **一次性并发**发出全部 lead、再一次性并发发出全部 mid：

- 总纲是**串行先行**的（biography.py:1562），它把 `system + 共享前缀` 送进缓存 —— 这是最有效的天然预热，应保留并确保它排在最前；
- 同批并发的请求彼此无法互相命中（缓存构建要数秒），所以 lead 批次里可能整批未命中、mid 批次才命中；
- **可选改进**：把每个批次拆成「第 1 个请求串行 → 其余并发」，
  或把总纲请求的 user 消息在 `共享前缀` 之后**多带一段所有篇目都会用到的公共文本**
  （现在的「篇目预告」正好是这个作用），以拉长可命中的公共前缀。
- 是否值得这么做，**由 §4.1 的 `prompt_cache_hit_tokens` 实测决定**（先测再改，勿凭猜）。

## 六、待确认项（请裁决）

1. **亲属头衔的「曾经持有」怎么写？**
   (a) `曾任高昌国王毗伽庞特勤`（信息最全，行内多一个词）
   (b) `故高昌国王毗伽庞特勤`（更史传，但对「失位未死」不准）
   (c) 只写现任头衔，无现任则退回纯名（最省，但妻父高昌国王这类会丢）
   → 建议 (a)，并在同一行出现多人时把「曾任」提到行首一次。

2. **亲属头的王子/公主称号格式？**
   (a) `楚国郡主苗映娘`（称号+名，与游戏显示一致，史书惯例）
   (b) `苗映娘（楚国郡主）`（名+括注，与现有 `prince` 字段渲染一致）
   → 建议 (a)。

3. **《本纪》《朝局》的纪事板块是否排除「谋害人命」模块？**
   终传里它占 71/117 条（2,640 字符），且《刺客列传》已整块承载。
   → 建议排除，板块头补一行「另有谋杀 N 人，详见《刺客列传·刀下诸魂》」。

4. **语言风味做到第几层？**
   (a) 只做 L1 档案行（≈+160 字符）
   (b) L1+L2 亲属语言标注（+250 字符）
   (c) L1+L2+L3 情节风味规则（+500 字符，风味最强）
   → 建议 (c)（用户诉求是「作为风味在文本中使用」，L3 才是真正的文本风味）。

5. **中段开篇回贴改摘要，摘要长度取多少？**
   Journal 用「前缀 260 + 结尾 180」。也考虑 (b) 只回贴开篇**最后一段**（约 300 字符，天然承接）。
   → 建议先按 Journal 口径 (a)，用 `【本板块大事】` 卡补锚点。

6. **是否接受「同篇 lead/mid 素材不相交」带来的写法变化？**
   现状 lead/mid 同料，模型会把同一批事实写两遍（拆成两段）；
   切片后两段各写一半人生，**篇幅与结构都会变**（更接近 Journal 的板块分工）。
   → 这是本方案唯一会显著改变成文风格的改动，需要用户确认。

7. **`【本板块大事】` 卡片的条数上限？**
   → 建议 3~6 条（超过即回到「长列表淹没问题」）。
